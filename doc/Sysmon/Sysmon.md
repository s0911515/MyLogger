これまでの試行錯誤を経て辿り着いた、現在のファイル監視基盤の全体像をシンプルに整理してピン留めします。

## 🎯 監視の目的

**「特定のフォルダ（`D:\tmp\`）において、誰が・いつ・何のプログラムを使って・どのようなファイル操作（コピー・通常削除・完全削除）を行ったか」を、ノイズなしで100%確実に追跡・記録する。**

---

## 🛠️ 設定したこと（何をしているか）

### 1. Sysmon設定（`config.xml`）

Windowsのカーネル（OSの根底）に対して、以下の3つの瞬間だけを検知するよう網羅的に網羅しました。

* **`FileCreate`（ID 11）**: `D:\tmp\` 配下への新規作成や他フォルダからの**コピー**を監視。
* **`FileCreate`（ID 11）**: 全ドライブの**ゴミ箱（`$Recycle.Bin`）への書き込み**を監視（通常削除を捕まえるための網羅）。
* **`FileDelete`（ID 23）**: `D:\tmp\` 配下での **Shift + Delete（完全削除）** を監視。

### 2. 出力スクリプト（`getLog.ps1`）

Sysmonが吐き出した生のイベントログを読み込み、以下の**特殊な自動翻訳**をかけて画面に整形出力します。

* ユーザーが「右クリック削除（ゴミ箱ポイ）」をした際、OS内部では「ゴミ箱へのファイル移動（Rename）」が行われます。
* スクリプトはゴミ箱に生成された管理用バイナリデータ（`$I` ファイル）を直接解析し、**「ゴミ箱に捨てられる前の元のファイルパス」を自動で復元**します。
* 同時に発生する不要な一時システムログ（ノイズ）は、正しいWindowsのパスの形（`D:\~` など）になっていないものを条件判定で100%自動除外します。

## ✅❌ Sysmonでできること／できないこと（検証済み）

`test.md` のテスト項目（新規作成・書き込み・コピー・ムーブ・リネーム・通常削除・完全削除）を実際にExplorer操作で検証し、Sysmon単体の検知能力を切り分けた。他の仕組み（USN Journal、セキュリティ監査ログ等）と組み合わせる設計をする際の前提情報としてここに記録する。

### できること

| 操作 | 検知 | 備考 |
|------|------|------|
| 新規作成 | ○ | `FileCreate`(ID 11) |
| 他フォルダからのコピー | ○ | `FileCreate`(ID 11)。貼り付け先パスに対して1件発生 |
| 通常削除（ゴミ箱移動） | ○ | `$Recycle.Bin`への`FileCreate`(ID 11)＋`$I`ファイル解析で元パス復元まで可能 |
| 完全削除（ゴミ箱を経由しない削除） | ○ | `FileDelete`(ID 23)。**ExplorerのShift+Deleteに限らず、PowerShellの`Remove-Item`等CLI/スクリプト経由の削除でも同様に発火する**（イベント自体はUIの操作方法を区別しない） |

### できないこと（Sysmon単体では検知不可）

| 操作 | 検知 | 理由 |
|------|------|------|
| 同一ボリューム内のムーブ（切り取り＆貼り付け、ドラッグ&ドロップ） | ✕ | NTFS的には`IRP_MJ_SET_INFORMATION`(`FileRenameInformation`)によるメタデータ更新のみで完結し、ファイル実体の作成・削除を伴わないため`FileCreate`(11)も`FileDelete`(23)も発火しない。2回の再現テストでも一貫して無検知を確認済み |
| リネーム | ✕ | 上記と同一の経路（メタデータ更新のみ）のため検知不可。新規作成直後にリネームした場合、ログにはリネーム前のデフォルト名が残る |
| 上書き保存（アプリによる） | △〜✕ | アプリの保存方式に依存。一時ファイルへの書き込み→リネームで置換する実装（メモ帳など）の場合、書き込み自体はリネーム経由になるため検知漏れが発生しうる |

### 設計上の含意

* Sysmonのファイル監視イベント（ID 11/23等）には、そもそも「リネーム」専用のイベント種別が存在しない。これはconfig.xmlの設定不足ではなく、Sysmonというツールの構造的な限界。
  * 興味深いことに、**レジストリ監視には`RegistryEvent (Key and Value Rename)`（ID 14）というリネーム専用イベントが存在する**（下表参照）。ファイル操作にだけリネーム専用イベントが用意されていない、というのがSysmonの設計上の非対称性。
* ムーブ・リネームの検知を埋めたい場合は、Sysmon以外の仕組み（NTFS USN Journal監視、Windowsセキュリティ監査ログの`4663`等）を別途組み合わせる必要がある。
* ノイズ面については、`D:\tmp\`配下・`$Recycle.Bin`以外の操作はテストで一切ログに出力されないことを確認済み（フィルタは意図通り機能している）。

## 🧩 Sysmonで指定可能な全イベントID一覧（Sysmon64.exe -s で確認、schema 4.90時点）

`config.xml`の`<EventFiltering>`内で`<RuleGroup>`に追加できるイベント種別は全部で **29種類**（＋内部エラー用の255）。現状使っているのは`FileCreate`(11)と`FileDelete`(23)の2つのみで、他26種類は未使用。

| ID | ルール名 | 内容 | 備考 |
|----|---------|------|------|
| 1 | ProcessCreate | プロセス生成 | 「誰のプログラムが」を特定する情報源。プロセス起点で追いたい場合に有用 |
| 2 | FileCreateTime | ファイルの作成日時が変更された | タイムスタンプ改ざん（タイムストンプ）の検知に使える |
| 3 | NetworkConnect | ネットワーク接続 | ファイル監視とは別軸 |
| 4 | ServiceStateChange | Sysmonサービス自体の状態変化 | Sysmonの生死監視用 |
| 5 | ProcessTerminate | プロセス終了 | |
| 6 | DriverLoad | ドライバのロード | |
| 7 | ImageLoad | DLL等イメージのロード | |
| 8 | CreateRemoteThread | リモートスレッド作成 | |
| 9 | RawAccessRead | ディスクの生読み取り | |
| 10 | ProcessAccess | プロセスへのアクセス | |
| **11** | **FileCreate** | **ファイル作成/上書き** | **✅使用中**（`D:\tmp\`配下、`$Recycle.Bin`） |
| 12 | RegistryEvent (Object create/delete) | レジストリキーの作成・削除 | |
| 13 | RegistryEvent (Value Set) | レジストリ値の設定 | |
| 14 | RegistryEvent (Key/Value Rename) | レジストリの**リネーム** | ファイルには相当イベントが無いことと対照的 |
| 15 | FileCreateStreamHash | ファイルストリーム作成 | 代替データストリーム(ADS)の検知に使える |
| 16 | ServiceConfigurationChange | Sysmon設定変更 | |
| 17 | PipeEvent (Created) | 名前付きパイプ作成 | |
| 18 | PipeEvent (Connected) | 名前付きパイプ接続 | |
| 19 | WmiEvent (Filter) | WMIフィルタ活動 | |
| 20 | WmiEvent (Consumer) | WMIコンシューマ活動 | |
| 21 | WmiEvent (Binding) | WMIフィルタ-コンシューマのバインド | |
| 22 | DnsQuery | DNSクエリ | |
| **23** | **FileDelete** | **完全削除（内容をアーカイブして記録）** | **✅使用中**（`D:\tmp\`配下） |
| 24 | ClipboardChange | クリップボードの内容変更 | コピー操作の裏付け情報になりうる |

| 28 | FileBlockShredding | ファイルシュレッディング（削除前上書き）を**ブロック** | 同上。アンチフォレンジック対策の防止に使える |
| 29 | FileExecutableDetected | 実行ファイルの作成検知 | |
| 255 | Error | Sysmon内部エラー | |

### 今後の拡張候補（ファイル監視強化の観点で）

* **ID 2 (FileCreateTime)**: コピー/移動後にタイムスタンプが改ざんされていないか検知したい場合に追加候補
* **ID 15 (FileCreateStreamHash)**: 代替データストリーム（ADS）を使った隠しファイル操作を検知したい場合に追加候補
* **ID 24 (ClipboardChange)**: コピー操作の「いつクリップボードに入れたか」を裏付けたい場合に追加候補
* **ID 26/27/28**: 完全削除の軽量記録や、実行ファイル作成・シュレッディングの防止まで踏み込みたい場合に追加候補

いずれもムーブ・リネームの検知漏れそのものを埋めるものではない（Sysmonの構造上不可能なため）が、周辺の証跡強化には使える。
