# 要件定義書：Windowsファイル入出力監視システム

## 1. はじめに（背景と目的）

重要情報の不正持ち出しや誤操作による情報漏洩リスクに備え、Windowsシステム上におけるファイル入出力およびユーザー操作を監視・記録する。本システムにより、万が一インシデントが発生した際の迅速な原因究明と、確実な監査トレース（証跡管理）を実現することを目的とする。

## 2. システム概要・全体方針

* **動作形態**: Windows OS上で動作するバックグラウンド常駐型アプリケーション（Windowsサービス、またはタスクスケジューラ等による常駐）。
* **監視アプローチ**: Windowsの標準機能である「監査ポリシー」を最大限に活用し、イベントログ等をフック/解析、またはAPIによる監視を行うことで、システムへの負荷を最小限に抑える。
* **データ管理**: 取得したログはローカル環境の軽量なリレーショナルデータベース（SQLiteなど）に一元管理する。
* **運用管理**: 監視対象ユーザーの定義や、データベースの肥大化を防ぐためのログローテーション設定は、外部の設定ファイルにより柔軟に変更可能とする。

---

## 3. 機能要件

### 3.1. 監査ポリシー自動設定機能

* **概要**: アプリケーション起動時に、監視に必要なWindows監査ポリシーが有効であるかを確認する。
* **動作**: ポリシー設定が不十分（無効または不足）である場合、アプリケーションがシステム権限を用いて強制的に必要な監査ポリシーを変更・有効化する。

### 3.2. ログ収集・監視機能

以下のイベントを検知し、共通のログフォーマット（4.1節参照）に変換して記録する。なお、**記録対象とするユーザー（またはユーザーグループ）は設定ファイル（INIやJSON等）にて指定可能**とする。

| 項番 | 監視対象操作 | 詳細仕様・条件 |
| --- | --- | --- |
| **①** | **ローカルファイル操作** | ・ローカル上でのファイルの「新規作成」「変更」「削除」を記録。<br>・「リネーム」「コピー」「ムーブ（移動）」時は、**変更前・変更後の両方のファイルパス**を記録。<br>・「読み込み（参照）」のみの場合は**記録対象外**とする。 |
| **②** | **ネットワークからの共有ファイルアクセス（被接続）** | ・外部のコンピュータから、自マシンの共有フォルダへ接続され、ファイルの読み書きが行われた際を記録。<br>・本操作に限り、**「読み込み（参照）」のみの場合も記録対象**とする。 |
| **③** | **ネットワークへの共有ファイルアクセス（接続）** | ・自マシンから外部のコンピュータ（共有フォルダ等）へ、ファイルを持ち出した操作（コピー、ムーブ）を記録。 |
| **④** | **ユーザー認証（ログイン/ログアウト）** | ・ユーザーのサインイン・サインアウトを記録。<br>・対象：コンソールログイン、リモートデスクトップ（RDP）ログイン、SMB認証（ネットワーク経由の認証）を含む。 |
| **⑤** | **RDPクリップボード経由のファイル持ち出し** | ・リモートデスクトップセッション中に、クリップボード共有機能を利用して、接続元（クライアント側）PCへファイルをコピーした操作を記録。 |

### 3.3. データ格納機能

* **データベース**: SQLite 等の簡易的なファイル型DBを使用する。
* **テーブル構成**: 上記①〜⑤のすべてのログを**単一の共通テーブル**に格納する。
* **識別要件**: レコードごとに、どの操作に該当するかを識別できる「操作種別（ログタイプ）カラム」を必ず設ける。
* **拡張性**: 将来的に、ログの「検索」「CSV出力」等を行う別アドオン（ツール）から参照・接続できる設計とする。

### 3.4. ログローテーション機能

* **概要**: ログの蓄積によるディスク容量の圧迫やDBパフォーマンスの低下を防ぐため、自動的なログローテーション（世代管理）を実装する。
* **動作**: 設定ファイルで定義された「ローテーション間隔（例：1ヶ月ごと、またはファイルサイズ上限）」に基づき、定期的に現在のDBファイルを切り替え、過去ログとして退避（アーカイブ）する。

---

## 4. 共通ログフォーマット（データ構造案）

全ログを格納する単一テーブルには、以下のカラムを定義する。

| カラム名（例） | データ型 | 必須/任意 | 説明 |
| --- | --- | --- | --- |
| `log_id` | INTEGER | 必須 | 主キー（自動連番） |
| `event_timestamp` | DATETIME | 必須 | 操作日時（秒、またはミリ秒単位） |
| `action_type` | VARCHAR | 必須 | 操作種別（例: `LOCAL_CREATE`, `SHARE_READ`, `LOGIN`, `RDP_CLIPBOARD` 等） |
| `target_user` | VARCHAR | 必須 | 操作を実行したユーザー名（およびドメイン/グループ） |
| `source_ip` | VARCHAR | 任意 | 操作元のIPアドレス（リモート接続、ネットワーク経由の場合に記録） |
| `source_path` | TEXT | 任意 | 操作対象のファイルパス（リネーム・移動前のパス、コピー元のパス） |
| `dest_path` | TEXT | 任意 | 操作対象のファイルパス（新規作成、変更、リネーム・移動後のパス） |
| `additional_info` | TEXT | 任意 | その他、イベントIDや詳細なコンテキスト（必要に応じて格納） |

---

## 5. 非機能要件

### 5.1. 性能・負荷軽減（最重要項目）

* **低負荷ロジックの検討**:
  * ファイル入出力（I/O）をカーネルレベルで常にフックする方式はシステム負荷が高くなるため、Windowsの「ファイル共有の監査」「オブジェクトアクセスの監査」などのイベントログ（Securityログ等）を非同期に検知・解析する方式を第一候補として検討する。
  * DBへの書き込み処理がファイルI/Oのボトルネックにならないよう、メモリ上のキュー（Queue）を挟んだ非同期書き込み（Bulk Insert等）の採用を検討する。
* **リソース制限**: 常駐時のCPU使用率、メモリ消費量の目標値を設定し、それを超えないよう制限をかける（例: 通常時CPU 5%以下など）。

### 5.2. セキュリティ（ログの保護）

* DBファイル（SQLite）および設定ファイル自体が一般ユーザーによって削除・改ざんされないよう、適切なWindowsのファイルシステム権限（NTFSアクセス権）を設定し、システムアカウント（SYSTEM）や管理者権限のみがアクセスできるように保護する。

### 5.3. 運用・保守性

* 将来的な「検索・出力ツール」との競合（DBロック）を防ぐため、SQLiteのWAL（Write-Ahead Logging）モードの有効化など、同時実行性を考慮した設計とする。
* ログローテーション実行時、検索・出力ツール側が一時的にアクセス不能になる時間を最小限に抑える、または影響が出ない排他制御を行う。
