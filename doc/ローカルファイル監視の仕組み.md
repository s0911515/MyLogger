# ローカルファイル監視(①)の仕組み — FileSystemWatcher と ETW

①(ローカルファイル操作監視)は `FileSystemWatcher` 単体ではなく、ETW(カーネルレベルのイベント
追跡)と組み合わせたハイブリッド構成になっている。単体では何ができて何ができないのか、ETWが
何を補っているのかを1つにまとめる。

実装は [`FileWatcherMonitor.cs`](../src/MyLogger/Monitors/FileWatcherMonitor.cs)(FileSystemWatcher側)
と [`EtwFileIoMonitor.cs`](../src/MyLogger/Monitors/EtwFileIoMonitor.cs)(ETW側)。実機調査の生データは
[FileSystemWatcher調査.md](FileSystemWatcher調査.md) を参照。

## 1. FileSystemWatcher でできること

「何が」「どこで」起きたかは正確に分かる。

| 操作 | 検知できる内容 |
|---|---|
| 作成 | パス(`Created`) |
| 変更 | パス(`Changed`)。ただし発火回数は書き込み方法により変動(1〜2件) |
| 削除 | パス(`Deleted`) |
| 同一フォルダ内リネーム | 変更前後両方のパス(`Renamed`、`OldFullPath`/`FullPath`) |

対象がファイルかフォルダかも `Directory.Exists`/`File.Exists` で判別できる(実装は
`FileWatcherMonitor.OnChanged` のフォルダ除外処理を参照)。

## 2. FileSystemWatcher の限界

### 2.1 「誰が」操作したかは一切分からない

`FileSystemWatcher` はパスの変化しか教えない。プロセス名・PID・実行ユーザーの情報を一切持たない。
これが本ドキュメント後半のETW補完が必要な最大の理由。

### 2.2 ノイズが多い(実機確認済み、[FileSystemWatcher調査.md](FileSystemWatcher調査.md)参照)

- ファイル作成 1回で `Created`+`Changed` が2〜3件、ほぼ同時に発火する
- 上書き保存は `Changed` が2件、追記は1件など、**発火回数は操作方法によって一定せず、回数から
  操作の種類を判別することはできない**
- ファイルの作成・変更・削除に伴い、**その1階層上のサブフォルダ自身にも `Changed` が飛ぶ**
  (ノイズ)。ただし実機調査では**監視ルート自身には伝播しなかった**という非自明な限定条件が
  確認されている

### 2.3 フォルダをまたぐ移動を意味的に検知できない

同一ボリューム内でも、エクスプローラーの「切り取り→貼り付け」等でフォルダをまたいで移動すると、
`Renamed` ではなく **`Deleted`(移動元)+`Created`(移動先)** に分解されて通知される
(実機確認済み)。`FileSystemWatcher` 自身には、この2つを「1回の移動」として統合する機能が無い。
→ 詳細は「4. MOVE の記録方法」参照。

### 2.4 コピー元のパスが分からない

コピー操作は「新規ファイルの作成」としてしか観測できず、元ファイルとの対応関係を追跡する手段が無い
(カーネルミニフィルタ等、`FileSystemWatcher`/ETW の範囲外の技術が必要)。MyLogger では
「コピー元候補プロセスの読み取り→書き込みをETWで時間相関させる」方式(`LOCAL_COPY`)を試作・実機
検証したが、(1) 小〜中サイズの通常のファイルコピーは Windows のキャッシュマネージャーの Fast I/O
経路で処理されるため ETW カーネル FileIO イベント(IRP 経由のイベントのみ発火)自体が発生せず検知
できない、(2) エクスプローラーの内部処理(ジャンプリスト更新等)を誤ってコピーと判定してしまう、
の2点により**不採用・実装を完全に削除した**(2026-07-05)。同じアプローチの再提案は不可。

### 2.5 バッファオーバーフローで取りこぼす可能性がある

`FileSystemWatcher` は OS 側バッファ(`ReadDirectoryChangesW`)経由のため、大量の同時イベントで
取りこぼす可能性がある。`FileWatcherMonitor` は `InternalBufferSize` を実用上の上限(64KB)まで
拡大し、`NotifyFilter` を `FileName|DirectoryName|LastWrite|Size` に絞り込んで発火量を抑えている
([FileWatcherMonitor.cs:84-89](../src/MyLogger/Monitors/FileWatcherMonitor.cs#L84-L89))。
発生時は `LOCAL_MONITOR_OVERFLOW` として検知はできるが、**欠落そのものは防げない**
(実機でのオーバーフロー再現は未検証、今後の課題)。

なお、イベントハンドラの処理速度もバッファの再発行(取りこぼし回避)に直結する。かつて実装していた
SACLフォールバック(後述)がハンドラ内で最大約900msの同期ブロッキングを行っていたことが判明し、
むしろオーバーフローリスクを高める構造だったため撤去した経緯がある。

## 3. ETW による補完

### 3.0 ETW とは何か

ETW(Event Tracing for Windows)は、ファイル監視専用の仕組みではなく、**Windows カーネル/OSが
標準で備える汎用のイベント追跡基盤**。プロセス起動、ネットワーク、ディスクI/O、レジストリ変更等、
様々な種類のイベントを高性能に配信できる、Windows のトレース機構そのもの。MyLoggerが使っているのは
その中の「NTカーネルロガー・FileIOプロバイダー」という1機能に過ぎない。

- **プロバイダー(Provider)**: イベントの発生源。今回使っているのはカーネルの FileIO プロバイダー
  (`KernelTraceEventParser.Keywords.FileIOInit | FileIO`、
  [EtwFileIoMonitor.cs:113-115](../src/MyLogger/Monitors/EtwFileIoMonitor.cs#L113-L115))。
  ファイルのオープン(`FileIOCreate`)・読み書き(`FileIORead`/`FileIOWrite`)・削除(`FileIODelete`)・
  リネーム(`FileIORename`)・フラッシュ(`FileIOFlush`)等のイベント種別を持つ。
- **セッション(Session)**: イベントを購読する側。`TraceEventSession`([EtwFileIoMonitor.cs:112](../src/MyLogger/Monitors/EtwFileIoMonitor.cs#L112))
  がこれにあたり、有効化したプロバイダーからのイベントをリアルタイムに受信する。カーネルプロバイダーの
  有効化には管理者権限が必要(`TraceEventSession.IsElevated()` で確認)。
- **システム全体が対象、パス単位のスコープ指定はできない**。`FileSystemWatcher` は「このフォルダだけ
  通知して」と登録できるが、ETWのカーネルFileIOプロバイダーは**PC上の全プロセス・全ファイルの
  I/Oイベントが無差別に流れてくる**。監視対象パスへの絞り込みは、アプリ側(`EtwFileIoMonitor` の
  `ClassifyPath`/`IsWatchedLocalPath`)で受信後にフィルタするしかない。これが「システム全体を対象に
  常時フックする方式は負荷が高い」(要件定義書5.1)と言われる所以で、本実装が③(ネットワーク/
  リムーバブル宛の書き込みだけに絞る)以外ではETWを補助的にしか使わない理由でもある。
- **IRP経由のイベントのみ発火し、Fast I/O経由は素通りする**。カーネルがファイルI/Oを処理する経路には
  従来型のIRP(I/O Request Packet)ディスパッチと、キャッシュマネージャーが介在する高速な Fast I/O
  経路の2種類があり、**ETWのFileIOイベントはIRP経由でのみ発火する**。小〜中サイズの通常のファイル
  読み書きは Fast I/O 経由で処理されることが多く、この場合 ETW からは見えない(「2.4 コピー元の
  パスが分からない」の根本原因もこれ)。`FileIOCreate`(オープン)はこの影響を受けず確実に発火するため、
  MyLoggerの相関はオープンイベントを軸に据えている。

### 3.1 何を補っているか

`EtwFileIoMonitor` はカーネルレベルの ETW FileIO イベント(`FileIOCreate`/`FileIOWrite`/
`FileIOFlush`)を、監視対象パス内に限り捕捉する。これにより「①の限界2.1」を補い、
`process`/`pid`/`target_user` を埋められる。

- `FileIOCreate`(ハンドルのオープン)は Fast I/O の影響を受けず確実に発生するため、この相関は
  高い信頼性で成立する(2.4のコピー元推定より確実)
- `FileIOWrite`(書き込み)も追跡するのは、メモ帳のように開いてから保存まで同じハンドルを保持する
  アプリでは、オープンと保存までに時間差があり、開いた瞬間の記録だけでは古すぎる候補になり得るため
- `FileIOFlush`(`FlushFileBuffers`)も追跡するのは、書き込みが Fast I/O 経由だと ETW に載らない
  ことがある保険として。フラッシュはキャッシュを迂回するため Fast I/O の影響を受けにくい
- 複数候補がある場合は `explorer.exe` を優先度を下げて選ぶ(フォルダ表示更新時のメタデータ再読み込みで
  本来の編集アプリの記録が上書きされるのを防ぐ、実機で確認された不具合への対策)
- Windows のキャッシュマネージャーによる `System`(PID 4)の遅延書き込みは、ファイルを開いた
  実プロセスへ差し戻す(`_openers` 対応表、[EtwFileIoMonitor.cs:44-47](../src/MyLogger/Monitors/EtwFileIoMonitor.cs#L44-L47))

これらの捕捉結果は、後述(3.5)の理由により**捕捉したその場で target_user まで解決してから**、
`local_fs_etw_open` テーブル(テーブルB)へ保存する。旧実装(2026-07-13以前)ではメモリ上の
`LocalFileOpenTracker` キャッシュとして保持し `FileWatcherMonitor` がリアルタイムに突き合わせて
いたが、この方式は撤回された(3.2参照)。

### 3.2 リアルタイム相関は万能ではない(この節は2026-07-13以前の実装に対する分析)

`EtwFileIoMonitor`(ETW)と `FileWatcherMonitor`(FileSystemWatcher)は**別々のOS通知の仕組みを、
別々のスレッドで処理している独立した経路**であり、どちらが先に届くかの保証が無い。
旧実装(`FileWatcherMonitor` がイベントを受け取ったその場で `LocalFileOpenTracker` を引く方式)では、
まだ ETW 側の処理が追いついていなければ、実際にはそのプロセスが操作したにもかかわらず相関に失敗した。
実機でも、**全く同じ操作を2回行って1回目は失敗・2回目は成功**という結果が確認されており、原因が
操作内容ではなくタイミングの偶然であることを裏付けている。

その他、コード上確認できる失敗要因:

- `EtwFileIoMonitor.OnCreate` は `ProcessID == 4`(System)によるオープンをそもそも無視する
  (Write/Flushと違い、Create時点でのSystem差し戻しの仕組みが無い)
- リアルタイム相関には猶予時間の限界があった(旧 `LocalFileOpenTracker` のTTLは30秒)

この分析が、3.5節の「リアルタイム相関を諦める」という設計転換の直接のきっかけになった。

### 3.3 相関に失敗した場合: 推測はしない

`target_user`/`process`/`pid` の解決に失敗した場合、以前は「現在アクティブな対話セッションの
ログオンユーザー」を近似値として使うフォールバック(WTS API 経由)を実装していたが、**MyLoggerの
実運用環境は複数ユーザーが同時ログインし得るため、この近似値は実際の操作者とは無関係な別ユーザーを
誤って記録するおそれがある**と判断し、2026-07-12 に完全撤回した。同様の理由で、オブジェクトアクセス
監査(SACL・イベント4663)へのフォールバックも実機検証の末に不採用・撤回している(ドライブルート
監視時にハングする、ハンドラ内の同期ブロッキングがオーバーフローリスクを高める、の2点が理由)。

現在は以下の2択のみ:

| ETW相関(3.5のバッチ突合) | target_user | process/pid |
|---|---|---|
| 成功 | WMI(`Win32_Process.GetOwner`)で解決した正確な値 | 正確 |
| 失敗 | `UNKNOWN`(推測しない) | null |

`target_user` は要件上必須項目だが、`UNKNOWN` でも値としては常に記録されるため要件は満たす。
「不正確な推測より、分からないと分かる方が良い」という判断。

### 3.4 逆に、ETW単体では①を実装できないのか

**「技術的に不可能」ではない。** ETWのFileIOプロバイダーはオープン・読み書き・削除・リネームの
イベントを一通り持っており、`FileIOCreate` はプロセスID/プロセス名も一緒に配信されるため、
理論上はETWだけで「誰が・何を」の両方を捕捉できる(実際、Sysinternalsの Process Monitor は
FileSystemWatcherを使わず、ETWのみでファイル操作を追跡している)。

それでも本実装がハイブリッド構成(①はFileSystemWatcherが主・ETWは補助)を選んでいるのは、
主に2つの理由による(README「なぜこの組み合わせなのか」も参照):

1. **リネームの前後パスを両方取れない。** `FileIORename` イベントは変更前の名前しか報告しない
   (3.0で触れた通りETWはIRP経由の生のイベントをそのまま流すだけの仕組みであり、
   `FileSystemWatcher` の `Renamed`(`OldFullPath`+`FullPath` のペア)のような、OS側で
   使いやすく整形されたイベントにはなっていない)。リネーム前後のパスを両方記録する要件を
   ETW単体で満たすには、`FileIOCreate`(ハンドルオープン、旧パス)と後続の情報イベントを
   `FileObject` 単位で自前で相関させる実装が別途必要になり、Process Monitor相当の作り込みが要る。
2. **システム全体が対象になるコスト(3.0)。** `FileSystemWatcher` は監視対象パスだけをOS側で
   絞り込んでくれるため、対象パス配下でイベントが起きた時だけ負荷が発生する。ETWは常に全プロセス・
   全ファイルのI/Oイベントを受信し続け、アプリ側で毎回フィルタする必要がある。要件定義書5.1が
   「カーネルレベルで常にフックする方式は負荷が高い」と明言している通り、①の主役をETWにすると
   常時フック方式そのものになってしまい、非機能要件の方針と正面から反する。

つまり「不可能」ではなく、「作れるが、OSが用意してくれる整形済みイベント(FileSystemWatcher)を
使わずに自前で同じものを組み立て直すことになり、常時全システムのI/Oを受信するコストも払うことになる
ため、割に合わない」というのが正確な結論。逆に③(ネットワーク/リムーバブル宛の書き込み)はローカル
用のセキュリティ監査イベントが存在しないため代替が無く、ETWを主役にせざるを得ない(README参照)。

### 3.5 結論: リアルタイム相関を諦め、テーブル分離+バッチ突合方式へ(2026-07-13)

3.2 の分析(独立した2経路である以上、タイミングのズレによる取りこぼしは構造的に避けられない)を
踏まえ、「①の場でリアルタイムに相関を試みる」こと自体を撤回した。

- **`local_fs_pending`(テーブルA)**: `FileWatcherMonitor` が検知したイベントを、属性(target_user/
  process/pid)を解決しないまま記録する。既存の重複排除・`LOCAL_MOVE`統合・Created直後のChanged
  抑制ロジック(FileSystemWatcher内部の話でETWのタイミングとは無関係)はそのまま維持。
- **`local_fs_etw_open`(テーブルB)**: `EtwFileIoMonitor` が監視対象パス内で捕捉したオープン/書き込み/
  フラッシュを記録する。**捕捉した瞬間に** WMI でユーザーまで解決してから保存する。これは、
  相関(テーブルAとの突合)が数分〜数日後に行われる可能性があり、その時点では操作元プロセスは
  とっくに終了していて WMI では引けなくなっているため(`Win32_Process.GetOwner` はプロセスが
  生きている間しか機能しない、という制約に対応した設計)。
- **[`tools/ReconcileLocalFs`](../tools/ReconcileLocalFs)**: テーブルA・Bをパス・時刻(前後30秒/5秒の
  窓)で突き合わせ、`activity_log`(テーブルC)へ最終レコードを書き込む、手動実行の別プロセス。
  テーブルA・Bはどちらも書き込み後変更しない(改ざん防止・監査証跡としての完全性)。テーブルAには
  `reconciled_at` を持たせ、何度再実行しても安全なようにしている。

この設計により「取りこぼし」自体は無くならないが(候補が見つからなければ `UNKNOWN`)、**わずかな
タイミングのズレによる本来防げるはずの取りこぼしは実質的に解消される**(バッチの実行タイミングまで
待てるため、旧実装のミリ秒〜TTL秒単位の猶予とは桁違いの猶予が持てる)。トレードオフは、①だけは
`tools/ReconcileLocalFs` を実行するまで `activity_log` に現れず、リアルタイム性が無いこと。

## 4. MOVE の記録方法(LOCAL_MOVE)

### 4.1 生の挙動

「2.3」の通り、フォルダをまたぐ移動は `Deleted`(移動元)+`Created`(移動先)に分解されて届く。
`Renamed` は発火しない。

### 4.2 MyLoggerの相関ロジック

`FileWatcherMonitor.OnCreatedOrDeleted` は、**同一ファイル名**の `Deleted`/`Created` が
`FileWatcher.MoveCorrelationWindowMs`(既定500ms)以内に両方発生したら、移動元/移動先パス付きの
`LOCAL_MOVE` として1件に統合する
([FileWatcherMonitor.cs:143-179](../src/MyLogger/Monitors/FileWatcherMonitor.cs#L143-L179))。

- 判定のため、`Created`/`Deleted` は最大 `MoveCorrelationWindowMs` 分だけ保留されてからDBに
  書き込まれる(`_pendingCreates`/`_pendingDeletes`)。片方しか来なければ、時間切れ後に通常の
  `LOCAL_CREATE`/`LOCAL_DELETE` として記録される(`FlushPendingMoves`、150ms間隔でスイープ)
- ファイル名の完全一致のみで相関するため、偶然同名のファイルが別フォルダで同時期に作成/削除された
  場合に誤って `LOCAL_MOVE` と判定するリスクは理論上あるが、時間窓を短くすることで低く抑えている
- `event_timestamp` には保留による遅延の影響を受けないよう、本来の発生時刻(検知した瞬間)を記録する。
  そのため `log_id`(DB書き込み順)と `event_timestamp` の順序が一致しない場合がある。時系列解析は
  `event_timestamp` でソートすること
- `MoveCorrelationWindowMs` を0以下にすると無効化できる(常に `LOCAL_CREATE`/`LOCAL_DELETE`)

### 4.3 MOVE時のプロセス/ユーザー解決

`LOCAL_MOVE` の `target_user`/`process`/`pid` も「3.5」のバッチ突合で解決される(移動先パスを
キーに `local_fs_etw_open` から探す)。ただし `MoveFileEx` 等、明示的な新規ハンドルオープンを
伴わない API で移動が実行される場合は、移動元・移動先のどちらのパスにも該当する行が無く
`process`/`pid` が付かないことがある(`target_user` は `UNKNOWN`)。

### 4.4 MOVE直後のChanged抑制

実機調査で、フォルダをまたぐ移動では `Deleted`+`Created` に加えて、移動先・移動元それぞれの
親フォルダ自身への `Changed`、および移動先の新ファイル自身への `Changed` も発火することを確認した
(下記5節と同じ仕組みで抑制される)。

## 5. Created 直後の Changed の抑制

「2.2」の通り、ファイルコピー等は OS 的に「作成」と「内容の書き込み」という別々の操作に分かれるため、
ユーザーから見れば1回の操作なのに `LOCAL_CREATE`+`LOCAL_CHANGE` の2件に分裂して記録されてしまう。
`FileWatcherMonitor` は **`Created`(または `LOCAL_MOVE` の移動先)の直後、`CreateChangeSuppressWindowMs`
(既定2000ms)以内に同一パスへ発生した `Changed` を記録しない**
([FileWatcherMonitor.cs:187-224](../src/MyLogger/Monitors/FileWatcherMonitor.cs#L187-L224))。
この抑制は `local_fs_pending`(テーブルA)への書き込み前、リアルタイムに行われる
(3.5のバッチ突合とは無関係、FileSystemWatcher内部の話であるため)。

`Created` がMOVE判定のため保留中(`_pendingCreates`)の間に `Changed` が先に届くケース(保留中の
`Created` が `Changed` より後にDBへ書き込まれてしまう、実機で確認された順序の逆転現象)も同様に
抑制する。パス(ファイル名)の完全一致でのみ判定するため、誤って無関係な `Changed` を抑制する
リスクは低い。実機の `QueryActivityLog` 出力で、コピー操作が `LOCAL_CREATE` 1件に統合されることを
確認済み。

## 6. まとめ

| 知りたいこと | 単体のFileSystemWatcherで分かるか | 補完する仕組み |
|---|---|---|
| 何が(パス)・どんな操作か | ○ | - |
| フォルダをまたぐ移動の統合 | ×(Deleted+Createdに分解) | `MoveCorrelationWindowMs` による相関(4節) |
| 作成直後の余計なChanged | ×(ノイズとして記録されてしまう) | `CreateChangeSuppressWindowMs` による抑制(5節) |
| 誰が(プロセス/ユーザー) | × | ETW捕捉(`local_fs_etw_open`)と`tools/ReconcileLocalFs`によるバッチ突合(3.5節)。リアルタイムでの相関は撤回済み。候補が無ければ推測せず`UNKNOWN` |
| コピー元のパス | × | 補完不可(2.4、対応を見送り済み) |
| 大量イベント時の取りこぼし | 発生し得る(2.5) | オーバーフロー検知のみ可能、防止は未対応 |

補足: ①は `local_fs_pending`(生イベント)→`tools/ReconcileLocalFs`(手動突合)→`activity_log`
(最終ログ)という3段構成になっており、突合を実行するまで最終ログには現れない。この設計に至った
経緯は3.5節を参照。
