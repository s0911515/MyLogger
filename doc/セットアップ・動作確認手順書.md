# MyLogger セットアップ・動作確認手順書

対象: [doc/要件定義書.md](要件定義書.md) に基づき実装した MyLogger を、実機にインストールし、
①〜⑤ すべての監視機能が正しく動作することを確認する手順書。
実装方式の詳細・設定項目の全リスト・制限事項は [README.md](../README.md) を参照。

## 0. 前提条件

- Windows 10/11 または Windows Server(x64)。管理者権限のアカウント。
- .NET 8 SDK がインストールされていること(`dotnet --version` で `8.x` 系が表示されること)。
- 監視対象ドライブ(既定は `D:\`)が存在すること。
- 以降の PowerShell コマンドは特記が無い限り**管理者権限の PowerShell**で実行する。

---

## 1. ビルド・インストール

### 1.1 サービスとしてインストール(推奨)

管理者権限の PowerShell でリポジトリルートに移動し、以下を実行する。

```powershell
.\scripts\install-service.ps1
```

このスクリプトは以下を自動で行う。

1. 既存の `MyLogger` サービスがあれば停止・削除
2. `dotnet publish` でビルドし `publish\` フォルダに出力
3. `MyLogger` サービスを登録(自動起動・異常終了時の自動再起動付き)
4. Windows イベントログ用のイベントソース登録
5. サービスを起動

実行後、以下のように `Running` 状態であれば成功。

```powershell
Get-Service MyLogger
# Status   Name       DisplayName
# ------   ----       -----------
# Running  MyLogger   MyLogger ファイル操作監視
```

サービス化した場合の設定ファイルは `publish\appsettings.json` になる点に注意(§2 参照)。

### 1.2 (代替) コンソールでのデバッグ実行

サービス化せず、設定変更のたびに素早く試したい場合はコンソールで直接実行できる。

```powershell
dotnet run --project src\MyLogger
```

- 管理者権限の PowerShell で実行すると全機能(①〜⑤・監査ポリシー自動設定・NTFS 権限保護)が動く。
- 非管理者で実行した場合は①(ローカルファイル操作)のみ動作し、②③④および監査ポリシー自動設定・
  ACL 保護はエラーログを出して当該機能のみ停止する(起動全体は失敗しない)。
- この場合の設定ファイルは `src\MyLogger\appsettings.json`。

**止め方**:

- フォアグラウンドのコンソールで実行している場合は `Ctrl+C` で止める。正常終了処理が走り、
  `ActivityLogger` がキューに溜まっている未書き込みイベントを最大 5 秒待って書き切ってから終了する。
- `Start-Process -WindowStyle Hidden` 等でバックグラウンド起動した場合(ウィンドウが無く `Ctrl+C` が
  効かない場合)は `Stop-Process -Id <プロセスID> -Force`(または `Get-Process MyLogger | Stop-Process -Force`)
  で止める。この場合は正常終了処理を経ないため、直前のごく一部の未書き込みイベントが失われる可能性がある
  (本実装はイベント受信ごとに即バッチ書き込みするため実害は小さい)。

以降の手順は 1.1(サービス)・1.2(コンソール)のどちらでも共通。差分がある箇所のみ明記する。

## 2. 設定

### 2.1 設定ファイルの場所

| 実行方法 | 設定ファイル |
|---|---|
| サービス(1.1) | `publish\appsettings.json` |
| コンソール(1.2) | `src\MyLogger\appsettings.json` |

編集後、サービスの場合は `Restart-Service MyLogger` で反映する。

### 2.2 試験前に確認しておきたい主要項目

```jsonc
"Monitoring": {
  "FileWatcher": {
    "Paths": [ "D:\\" ]     // ①の監視対象。試験用のフォルダがこのドライブ配下にあることを確認
  },
  "MonitoredUsers": [],     // 空 = 全ユーザー監視。絞り込み試験をする場合のみ変更(§6.9)
  "Rotation": {
    "MaxSizeMB": 500        // ローテーション試験をする場合のみ小さい値に変更(§6.8)
  }
}
```

設定項目の全リストは README.md の「設定」節を参照。

## 3. 起動確認(共通の事前チェック)

サービスを起動、またはコンソールで `dotnet run` した直後に、以下 2 点を確認する。

### 3.1 監査ポリシー自動設定(要件 3.1)の確認

```powershell
auditpol /get /subcategory:"ファイル共有"
auditpol /get /subcategory:"詳細なファイル共有"
auditpol /get /subcategory:"ログオン"
auditpol /get /subcategory:"ログオフ"
```

いずれも「成功と失敗」(英語 OS では "Success and Failure")になっていれば OK。
MyLogger 起動前に無効だった場合でも、起動しただけで自動的に有効化される。

### 3.2 NTFS 権限保護(要件 5.2)の確認

```powershell
icacls C:\ProgramData\MyLogger\data
icacls (サービス: "publish\appsettings.json" / コンソール: "src\MyLogger\appsettings.json")
```

`NT AUTHORITY\SYSTEM:(F)` と `BUILTIN\Administrators:(F)` のみが表示され、
`Users`/`Everyone`/`Authenticated Users` 等が含まれていなければ OK。

### 3.3 イベントログでの動作確認

サービスとして動かしている場合、動作状況は Windows イベントログ(アプリケーションログ、
ソース名 `MyLogger`)にも出力される。

```powershell
Get-EventLog -LogName Application -Source MyLogger -Newest 20
```

`ローカル監視を開始しました`、`ETW 監視を開始しました`、`共有フォルダアクセス監視...を開始しました`、
`ログイン/ログアウト監視...を開始しました` が出ていれば全 Monitor が起動できている。
エラー(`fail`)が出ている場合は §8 トラブルシューティングを参照。

## 4. ログ確認用ツール

DB は SQLite(`C:\ProgramData\MyLogger\data\activity.db`)。付属の簡易ツールで内容を確認できる。
ACL 保護(§3.2)により **管理者権限でないと読み取れない**点に注意。

```powershell
# 件数サマリ + 直近20件を表示
dotnet run --project tools\QueryActivityLog

# 任意の SQL を実行 (第1引数は DB パス、既定のままなら省略せず明示的に渡す)
dotnet run --project tools\QueryActivityLog -- C:\ProgramData\MyLogger\data\activity.db "SELECT * FROM activity_log WHERE action_type='LOCAL_CREATE' ORDER BY log_id DESC LIMIT 5"
```

文字化けする場合は Windows Terminal または PowerShell 7(pwsh)での実行を推奨する
(既定の PowerShell 5.1 コンソールでは日本語が化けることがある)。

以降の各試験は、操作を行った後にこのツールで該当する `action_type` の行が
正しい内容(`target_user`/`source_path`/`dest_path` 等)で記録されているかを確認する形で進める。

**①(ローカルファイル操作)だけは追加の手順が必要。** ①のイベントはまず `local_fs_pending` テーブルに
未帰属のまま記録され、以下のツールで手動突合しないと `activity_log` には現れない
(詳細は [doc/ローカルファイル監視の仕組み.md](ローカルファイル監視の仕組み.md) 参照)。

```powershell
dotnet run --project tools\ReconcileLocalFs -- C:\ProgramData\MyLogger\data\activity.db
```

何度実行しても安全(未処理分だけが処理される)。②③④⑤はこの手順は不要(リアルタイムに
`activity_log` へ記録される)。

## 5. 監視機能ごとの動作確認(試験)

いずれの試験も、操作後 5〜10 秒待ってから §4 のツールで確認すること
(非同期キュー + バッチ書き込みのため、即座には反映されない)。

### 5.1 ① ローカルファイル操作

`FileWatcher.Paths` に含まれるドライブ(既定 `D:\`)配下で操作する。

```powershell
$dir = 'D:\MyLoggerTest'
New-Item -ItemType Directory -Force -Path $dir | Out-Null

# 作成
Set-Content -Path "$dir\a.txt" -Value "hello"
# 変更
Add-Content -Path "$dir\a.txt" -Value "world"
# リネーム
Rename-Item -Path "$dir\a.txt" -NewName "b.txt"
# 削除
Remove-Item -Path "$dir\b.txt"
```

§4 の `ReconcileLocalFs` を実行してから確認する。

期待結果: `LOCAL_CREATE`(dest=a.txt)→`LOCAL_CHANGE`(dest=a.txt)→
`LOCAL_RENAME`(source=a.txt, dest=b.txt)→`LOCAL_DELETE`(source=b.txt)が記録される。
`target_user` は ETW 相関(§4上部参照)が成功していれば操作したユーザー名(`DOMAIN\user`)、
失敗していれば `UNKNOWN` になる。相関の成否は毎回変動し得る(実機で同一操作でも成功/失敗が
入れ替わることを確認済み)ため、`UNKNOWN` が出ても異常ではない。`LOCAL_CREATE`/`LOCAL_CHANGE`
自体が記録されていることが重要な確認ポイント。

### 5.2 ② ネットワークからの共有ファイルアクセス(被接続)

同一マシンからの UNC アクセスでも Windows のセキュリティ監査上は
「共有への外部アクセス」として扱われるため、2 台目の PC が無くても試験できる。

```powershell
# 試験用共有フォルダの作成
$shareDir = 'C:\MyLoggerShareTest'
New-Item -ItemType Directory -Force -Path $shareDir | Out-Null
Set-Content -Path "$shareDir\shared.txt" -Value "share-test"
New-SmbShare -Name 'MLTest' -Path $shareDir -FullAccess Everyone

# UNC 経由でアクセス (コンピュータ名は $env:COMPUTERNAME)
Get-Content "\\$env:COMPUTERNAME\MLTest\shared.txt"
Set-Content -Path "\\$env:COMPUTERNAME\MLTest\shared.txt" -Value "updated"
```

期待結果: `SHARE_CONNECTED`(共有への接続)、`SHARE_READ`/`SHARE_WRITE`
(`dest_path`=`shared.txt` の実パス、`target_user`・`source_ip` 付き)が記録される。
`source_ip` はループバック(`127.0.0.1` 等)またはコンピュータ名で解決された IP になる。

試験後の後片付け:

```powershell
Remove-SmbShare -Name 'MLTest' -Force
Remove-Item -Recurse -Force $shareDir
```

### 5.3 ③ ネットワークへの共有ファイル持ち出し(接続)

自マシンから外部(共有フォルダ・USB 等)へのコピーを試験する。5.2 で作成した共有、
または USB メモリが利用できればそちらでもよい。

```powershell
# 例: 5.2 の共有 (\\<コンピュータ名>\MLTest) を使う場合
New-SmbShare -Name 'MLTest' -Path 'C:\MyLoggerShareTest' -FullAccess Everyone -ErrorAction SilentlyContinue
Copy-Item -Path 'D:\MyLoggerTest\sample.txt' -Destination "\\$env:COMPUTERNAME\MLTest\sample.txt"
```

(`D:\MyLoggerTest\sample.txt` が無ければ事前に `Set-Content` 等で作成しておく。)

期待結果: `NETWORK_EXFIL_WRITE`(`dest_path`=書き込み先 UNC パス、`additional_info` に
`process`(explorer/pwsh 等)・`pid`・`bytes` が入る)が記録される。
USB メモリへコピーした場合は `REMOVABLE_WRITE` になる。

> 注意: コピー元パス(`source_path`)は本実装では記録されない(README「制限事項・注意」参照)。

### 5.4 ④ ユーザー認証(ログイン/ログアウト)

コンソールログインの場合はサインアウト・再サインインで確認する。

```powershell
# サインアウト (実行すると即座にログオフされるため、保存していない作業がないか確認してから実行)
shutdown /l
```

再度サインインした後、§4 のツールで確認する。

期待結果: サインアウト時に `LOGOUT`、サインイン時に `LOGIN`
(`target_user`=サインインしたユーザー、`additional_info` に `Console`/`RDP`/`Network(SMB等)` の
ログオン種別)が記録される。

RDP(リモートデスクトップ)でこの PC に接続できる環境があれば、RDP 接続・切断でも同様に
`LOGIN`(種別 `RDP`)/`LOGOUT` が記録されることを確認できる。

### 5.5 ⑤ RDP クリップボード経由のファイル持ち出し(環境がある場合のみ)

この試験には、**MyLogger をインストールした PC(RDP サーバー役)へ RDP 接続できる
別クライアント PC**が必要。無い場合は本項をスキップしてよい(README に検知の仕組みは記載済み)。

1. 別 PC からこの PC へリモートデスクトップ接続する。
2. RDP セッション内(この PC 側の画面)で、ローカルファイル(例: `D:\MyLoggerTest\sample.txt`)を
   エクスプローラーでコピー(Ctrl+C)する。
3. 接続元(クライアント側)PC のデスクトップ等にペースト(Ctrl+V)する。

期待結果: この PC 側の DB に `RDP_CLIPBOARD_COPY`(`source_path`=コピーしたローカルファイル、
`additional_info` の `process`=`rdpclip`)が記録される。

### 5.6 ログローテーション(要件 3.4)の試験(任意)

閾値を一時的に下げて強制的にローテーションを発生させる。

1. 設定ファイル(§2.1)の `Rotation.MaxSizeMB` を `1` に変更し、サービスなら再起動
   (コンソール実行なら再度 `dotnet run`)。
2. 大量にイベントを発生させて DB を 1MB 超まで増やす。

   ```powershell
   $dir = 'D:\MyLoggerTest\rotation'
   New-Item -ItemType Directory -Force -Path $dir | Out-Null
   1..3000 | ForEach-Object {
       Set-Content -Path "$dir\f$_.txt" -Value "x"
       Remove-Item "$dir\f$_.txt"
   }
   ```

3. 数十秒待ってから確認する。

   ```powershell
   Get-ChildItem C:\ProgramData\MyLogger\data\archive
   ```

   `activity-yyyyMMdd-HHmmss.db` という名前のファイルが作成され、
   `C:\ProgramData\MyLogger\data\activity.db` は新しい空の DB に切り替わっていれば成功。

4. 試験後は `Rotation.MaxSizeMB` を元の値(既定 `500`)に戻しておくこと。

### 5.7 監視対象ユーザー絞り込み(任意)

1. 設定ファイルの `MonitoredUsers` に自分のユーザー名以外のダミー名(例: `["dummyuser"]`)を設定し、
   サービスなら再起動。
2. §5.1 のようにローカルファイル操作を行う。
3. §4 のツールで確認する。→ 自分のユーザーによる操作は記録されない(フィルタで除外される)ことを確認。
4. `MonitoredUsers` に自分のユーザー名(`DOMAIN\user` または `user` 部分のみ)を追加し、
   再度操作 → 今度は記録されることを確認。
5. 試験後は `MonitoredUsers` を `[]`(空)に戻しておくこと。

## 6. アンインストール

```powershell
.\scripts\uninstall-service.ps1
```

サービスの停止・削除のみを行う。DB ファイル(`C:\ProgramData\MyLogger`)は削除されないため、
完全に削除したい場合は管理者権限で別途 `Remove-Item -Recurse -Force C:\ProgramData\MyLogger` を実行する
(ACL 保護により管理者権限が必要)。

## 7. トラブルシューティング

| 症状 | 確認・対処 |
|---|---|
| サービスが `Running` にならない / 直後に停止する | `Get-EventLog -LogName Application -Source MyLogger -Newest 20` でエラー内容を確認。多くは管理者権限不足(サービスは既定で LocalSystem で動くため通常は問題にならないが、手動でユーザーアカウントに変更した場合は要注意)。 |
| ②③④ が記録されない、`ETW 監視を開始しました` 等のログが出ない | 管理者権限で起動しているか確認(§1.2 の非管理者時の制限を参照)。 |
| `auditpol` の値が反映されない | MyLogger 自体を一度再起動する(起動の度に強制設定するため)。手動で `auditpol /set` した場合、次回 MyLogger 起動時に上書きされる。 |
| DB ファイルが見つからない/読めない (`QueryActivityLog`) | ACL 保護(§3.2)のため管理者権限で実行しているか確認。`DataDirectory` 設定を変更していないか確認。 |
| ローカル操作の `target_user` が実際と異なる/`UNKNOWN` になる | README「制限事項・注意」参照。複数ユーザーが同時ログオンしている環境では対話セッションからの近似値になるため不正確な場合がある。 |
| ③⑤(ネットワーク持ち出し/RDPクリップボード)の `target_user` が `UNKNOWN` になる | WMI(`Win32_Process.GetOwner`)によるプロセス所有者解決が一時的に失敗した可能性がある。失敗結果は 5 秒しかキャッシュされないため、同じプロセスによる後続の操作では自動的に解決できることが多い(README「target_user の解決方法」参照)。継続して失敗する場合は `appsettings.json` の `Logging:LogLevel:Default` を `Debug` にして再起動し、`Get-EventLog -LogName Application -Source MyLogger` で `ProcessUserResolver` のログを確認する。 |
| ②の共有アクセスが記録されない | `auditpol /get /subcategory:"ファイル共有"` / `"詳細なファイル共有"` が有効か確認。共有自体が正しく作成されているか `Get-SmbShare` で確認。 |
| 文字化けする | Windows Terminal または PowerShell 7(pwsh)で実行する。`chcp 65001` も有効な場合がある。 |
